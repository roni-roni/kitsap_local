# Class 5 - State management and architecture

**New this week (bold):** Riverpod, repositories, the Government tab (officials via data script), and the curated Events tab.

## Learning goals

- Explain why state management exists, in one sentence.
- Structure the app in layers so data sources can change without touching screens.
- Handle loading, data, and error states as a first-class concern.

## Concepts

- State: ephemeral (a checkbox) vs shared (selected filters, loaded data).
- **Riverpod:** `ProviderScope`, `Provider`, `FutureProvider`, `NotifierProvider`, `ref.watch` / `ref.read`, `AsyncValue` and `.when(data/loading/error)`.
- **Repository pattern:** an abstract class (`ParksRepository`) with a bundled-JSON implementation now and an HTTP implementation later.
- Dependency injection through providers; overriding providers in tests.
- Feature folders, and the layering rule in [Architecture](../07-architecture.md).
- Small scripts as part of a data pipeline: fetch, parse, validate, write JSON. (Python is used in `tools/`; discuss why the scripts are outside the app.)

## In class

1. `flutter pub add flutter_riverpod`; wrap the app in `ProviderScope`.
2. Refactor Help and Parks: `Screen -> Provider -> Repository -> JSON`. Move Park filters into a `Notifier`.
3. Every screen renders `AsyncValue`: spinner, error with retry, empty state, data.
4. **Officials.** Run `python3 tools/county_officials.py --url <county page> --list-tables`, pick the table, map columns, produce `data/generated/officials.json`. Review the output by eye; fix mapping issues. Record the source URL and retrieval date in the issue.
5. **Government tab.** Officials list and detail (phone/email links). Meetings: a curated list (county plus each city) that links to the official agenda page.
6. **Events tab.** Read `data/events.json`, hide past events, group by day, show the source. Curate 15-20 real, verified upcoming events.

## Scraping etiquette (teach this)

Check the site's terms and `robots.txt`; identify yourself in the User-Agent; fetch rarely (not on every app launch, not on every build); store the result; never overload someone's server. Consider emailing the county for a proper data export.

## Discussion prompts

- Keep providers small and named for what they hold.
